# React Native Spy — Landing Page

Marketing site for the [React Native Spy](../README.md) desktop debugger.
React 18 + Vite, no CSS framework, no animation library. Deployed to GitHub Pages
by [.github/workflows/pages.yml](../.github/workflows/pages.yml) on every push to
`main` that touches this folder.

Live at <https://vaibhav-s-mahajan.github.io/React-native-spy/>.

## Run it

```bash
npm install
npm run dev        # http://localhost:5180
npm run build      # → dist/, prerendered
npm run preview    # serve the production build
```

## Prerendering

`npm run build` is three steps, and the third is the one that matters for SEO:

1. `vite build` — the client bundle, plus a shell `index.html`
2. `vite build --ssr` — a server bundle in `.ssr-dist/` (temporary, gitignored)
3. `scripts/prerender.mjs` — renders the page to a string and writes real HTML

Without step 3, `dist/index.html` ships an empty `<div id="root">`. Google
executes JavaScript, but Slack, X, LinkedIn, Discord and most other crawlers do
not — they would see a blank page with no copy and no card. Prerendering means
the HTML is complete before any JS runs; `src/main.jsx` then *hydrates* that
markup instead of mounting over it.

The prerender step also writes `404.html` (a copy of the page, so a mistyped URL
still shows the site), `robots.txt` and `sitemap.xml`, and it **fails the build**
if the rendered HTML comes back suspiciously small — a component that throws
during server rendering cannot quietly ship as a blank page.

### Keeping components prerender-safe

Anything that touches `window`, `document` or `navigator` must do it inside
`useEffect`, never during render. Two places earn special mention:

- **`Reveal.jsx`** renders *visible* first and only hides itself in a layout
  effect, and only for elements below the fold. If it started hidden, every
  section would ship at `opacity: 0` — which crawlers read as hidden content, and
  which leaves the page blank if the bundle fails to load.
- **`usePlatform`** returns `null` on the first render by design, so the download
  button starts platform-neutral instead of hydrating into a different label.

### SEO surface

`src/data/site.js` holds the deployment identity — base path, origin, canonical
URL, OG image dimensions. Change those values and `vite.config.js`, the canonical
tag, the OG/Twitter tags and the sitemap all follow. Nothing else hardcodes the
domain, so moving to a custom domain is a one-file edit (set `BASE` to `'/'`).

`scripts/prerender.mjs` injects everything that needs an absolute URL, plus two
JSON-LD graphs built from `content.js` rather than hand-maintained:
`SoftwareApplication` (app-style result: OS, price, license, feature list) and
`FAQPage` (eligible for the expandable FAQ treatment). Because they are derived
from the same module the page renders, the structured data cannot drift from the
visible copy — which is exactly the mismatch that earns a manual action.

Static tags stay in `index.html`. Do not add canonical or OG tags there by hand;
they would be duplicated.

## The social card

`public/og.png` is generated by `scripts/make-og-image.py` (needs Pillow):

```bash
python3 scripts/make-og-image.py
```

Regenerate and commit it when the product name, tagline or panel list changes.
It is a script rather than a checked-in export because the card restates copy
that lives in `content.js`, and a binary nobody knows how to rebuild goes stale
silently. SVG is not an option here — no major social platform accepts it.

## Why no Tailwind or Framer Motion

The whole page is ~48 kB of CSS and ~66 kB of gzipped JS, and almost all of the
motion is CSS keyframes plus `IntersectionObserver`. Adding a utility framework or
an animation runtime would have cost more bytes than the page itself. The three
places JavaScript drives motion are the ones CSS genuinely cannot do:

| Hook | Job |
| ---- | --- |
| `useInView` | fires once when an element scrolls into view, so entrances do not replay |
| `useCountUp` | `requestAnimationFrame` counter with an `easeOutExpo` curve |
| `useLiveFeed` | synthetic event stream that drives the animated app mock |
| `useMousePosition` | pointer spotlight + hero parallax, written to CSS vars to avoid re-renders |
| `useReducedMotion` | tracks `prefers-reduced-motion` so JS motion opts out like CSS does |
| `usePlatform` | detects macOS/Windows/Linux so the download button leads with the right build |

## Structure

```
src/
  data/content.js        every string on the page, sourced from ../docs
  hooks/                 the five hooks above
  components/
    Background.jsx       fixed grid + colour blooms + grain + scanline
    Nav.jsx              sticky nav, scroll progress, active-section tracking
    Hero.jsx             headline, actions, stats strip
    AppMock.jsx          animated recreation of the debugger window
    Problem.jsx          the gap the product fills
    Features.jsx         six-panel showcase (accessible tablist)
    Setup.jsx            four-step integration walkthrough
    Compare.jsx          capability matrix + 12 copy-as formats
    Protocol.jsx         data-flow diagram, SDK patches, event protocol
    Extras.jsx           secondary capabilities
    Faq.jsx              accordion
    Download.jsx         conversion block + platform targets
    DownloadButton.jsx   platform-aware split button with an all-builds menu
    Footer.jsx           links into docs/
    Button/CodeBlock/Reveal/Logo   primitives
```

Design tokens in `src/index.css` mirror `src/renderer/styles/theme.css` from the
desktop app, so the site and the product share one visual language. Copy edits
should only ever touch `src/data/content.js`.

## The download button

`DownloadButton.jsx` is a split control: the wide half names the visitor's own OS
("Download for macOS"), the caret half opens a menu of every build. Detection is
deliberately conservative — it only distinguishes macOS, Windows and Linux, and
falls back to a neutral "Download latest release" when it cannot tell, including
on Android and iOS. Naming the wrong OS is worse than naming none.

CPU architecture is not detected. `getHighEntropyValues()` is Chromium-only and
Rosetta muddies the answer on macOS, so Apple Silicon and Intel builds are both
offered explicitly in the menu instead of guessed at.

The menu uses real `role="menu"`/`menuitem` semantics with arrow-key, Home/End,
Escape and click-outside handling, and restores focus to the toggle on close.

Build targets in `PLATFORMS` (`src/data/content.js`) mirror the `mac`/`win`/`linux`
blocks in [electron-builder.yml](../electron-builder.yml). If those targets change,
update both.

## Content accuracy

Every number and capability claim is drawn from the app's own docs rather than
invented: the 2000-per-device caps and 500-entry log buffer from
[configuration.md](../docs/configuration.md), the six panels from
[features.md](../docs/features.md), the event protocol from
[client-sdk.md](../docs/client-sdk.md), and the plan/apply setup flow from
[architecture.md](../docs/architecture.md). The comparison table marks rivals
"partial" rather than "missing" where they do something in a limited way —
overstating a gap is the fastest way to lose a developer audience.

`PRODUCT.repo` in `src/data/content.js` is the single source for every GitHub and
docs link on the page. It matches the `publish` block in
[electron-builder.yml](../electron-builder.yml), which is where `electron-updater`
looks for new versions. Deployment URLs are separate — those live in
`src/data/site.js`.

## Accessibility

The desktop app's own UI audit flagged mouse-only interaction as a P1 issue, so
this page does not repeat it:

- Skip link, single `h1`, ordered headings
- The features showcase is a real tablist with arrow-key/Home/End navigation and
  roving `tabIndex`
- FAQ uses buttons with `aria-expanded`/`aria-controls`; collapsed answers are
  hidden with `visibility` so they leave the a11y tree without breaking the
  height transition
- Comparison marks pair colour with an icon and screen-reader text, never hue alone
- Focus rings are visible on every surface
- All motion, including the JS-driven feed, stops under `prefers-reduced-motion`

## Note on the dev server

`package.json` pins a `browserslist` field on purpose. Without it, browserslist
walks up past the repo root looking for a config file and can fail with `EPERM`
in sandboxed or restricted-permission environments, which breaks the Babel
transform and the dev server with it.
